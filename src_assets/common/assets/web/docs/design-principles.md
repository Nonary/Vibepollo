# Vibepollo design principles

These principles define the Vibepollo interface. **Must** indicates release acceptance; **should** indicates the default unless a documented product constraint requires an exception.

| # | Principle | Why | Correct use | Misuse to avoid | Primary surfaces |
|---:|---|---|---|---|---|
| 1 | **Build a quiet utility, not a gaming promotion.** | People come here to configure, launch, and diagnose a service. Ornament competes with those tasks. | Use neutral surfaces, restrained accent color, border-led grouping, concise copy, and at most one primary action per region. | Decorative gradients, glow, autoplay media, promotional carousels, equal-weight card mosaics, or shadows around every section. | All pages, especially Dashboard and Library |
| 2 | **Put readiness and the next action first.** | A technical status is useful only when a person can understand its consequence and respond. | Lead with a human-readable state, its cause when known, and a visible repair, approve, retry, stop, or configure action. | Leading with raw metrics, codes, or diagnostics; using color as the only state cue. | Shell, Dashboard, Devices, Sessions, Maintenance |
| 3 | **Use one hierarchy everywhere.** | Shared rhythm makes dense technical information predictable and keeps pages from becoming separate products. | Consume semantic/component tokens for spacing, type, color, radius, focus, and motion. Reuse page headers, settings groups, status rows, and action bars. | Raw palette values, arbitrary spacing, page-specific focus styles, or a card around every setting. | All pages |
| 4 | **Reveal detail progressively.** | Most users need an answer and an action; experts still need the evidence beneath them. | Show summaries first, expand diagnostics in-place or in a preview drawer, and use a full page for deep multi-section editing. | Hiding required instructions in tooltips, exposing raw payloads first, or putting long editing workflows in drawers. | Dashboard, Devices, Sessions, Logs, Settings |
| 5 | **Make common actions direct and dangerous actions deliberate.** | Fast routine work and safe recovery require different interaction costs. | Keep the primary routine action visible; place secondary actions in overflow; isolate danger zones and confirm irreversible actions with explicit consequences. | Swipe-only actions, filled danger buttons in ordinary rows, ambiguous icon-only actions, or mixing reset controls with normal updates. | Library, Devices, Sessions, Settings, Maintenance |
| 6 | **Use a stable state language.** | The same service condition must mean the same thing everywhere and to assistive technology. | Map every state to text, icon, semantic color, announcement policy, and available action. Use the shared catalogue for connected, streaming, pending, degraded, blocked, error, saving, stale, empty, partial, and unavailable. | Synonymous labels for the same state, status-colored metadata badges, or announcing every numeric update. | Shell, Dashboard, Devices, Sessions, Integrations, Logs |
| 7 | **Preserve context while data changes.** | Streaming metrics and logs update continuously; movement makes comparison and intervention harder. | Keep rows, selection, filters, scroll, and numeric widths stable. Reorder only after an explicit sort change or refresh. Virtualize large libraries and logs. | Live row reordering, layout shifts from changing numbers, resetting filters on navigation, or animating every log entry. | Dashboard, Library, Devices, Sessions, Logs |
| 8 | **Keyboard and semantics are first-class.** | Desktop keyboard use is primary, and accessible semantics benefit every input method. | Use native buttons, links, labels, tables, and headings; visible 2 px focus rings; documented composite-widget arrow keys; equivalent pointer and keyboard menus. | Clickable generic containers, ARIA grids for read-only tables, placeholder-only labels, or shortcuts as the only discovery path. | Shell, Library, Settings, Devices, Sessions, Logs |
| 9 | **Reflow when content fails, not when a device name changes.** | Real strings, zoom, localization, and available width determine whether a layout works. | Start from 480/768/1024/1440 px behavioral breakpoints, then validate at 200% text and 400% zoom. Stack actions and fields before truncating essential content. | Desktop-only fixed widths, page-level horizontal scrolling, tooltip-only full values, or mobile gestures without buttons. | All pages |
| 10 | **Motion must explain change and respect preference.** | Short, consistent motion can preserve spatial context; gratuitous movement distracts and can harm users. | Use 80/160/240 ms tokens for controls and overlays, 320 ms only exceptionally, and opacity/small transforms for transient layers. Provide immediate/static reduced-motion behavior. | Bouncy transitions, animated page navigation, parallax, traveling skeletons, autoplay previews, or undocumented animation. | Shell overlays, dialogs, drawers, loading states |

## Non-negotiable release checks

- Both themes use the same semantic contracts: dark keeps the lunar indigo/cyan identity, while light uses a restrained solar amber treatment. Brand color never weakens text, control, or focus contrast.
- Default density is medium. Compact variants are limited to data-heavy or expert surfaces until a global mode is validated.
- Every page has loading, empty, error, disabled/unavailable, and narrow-layout behavior where those states apply.
- WCAG 2.2 AA, visible keyboard focus, forced-colors resilience, reduced motion, 200% text resize, and 400% zoom are implementation requirements rather than later polish.
- A page may compose public patterns, but it must not redefine primitive colors, spacing, focus, or motion.
