# Hardware metrics v1

Enable `hardware_metrics` (default disabled) to allow an enabled paired streaming client with View or Launch permission to query `GET /api/hardware-metrics` on the streaming HTTPS port (`HttpsPort` from `/serverinfo`, normally 47984). The admin console does not authenticate this route. Authenticated HTTPS discovery advertises `HardwareMetricsVersion=1` when enabled; plain HTTP advertises 0 and has no metrics route.

The exact certificate-bound client must own a RUNNING video transport. Normal and Remote Monitor video qualify; input-only, pending, stopping, ended and other-client streams do not. Queries only observe transport state and never clean, stop or join sessions. Authority and stream presence are checked again after the sampling wait.

Live enablement and interval changes become visible together when configuration parsing and its apply side effects complete successfully. Discovery and requests continue using the previous completed settings during reset/parsing or a failed apply; successful removal of both keys restores disabled/1000 ms. Readers do not wait on the configuration apply gate. Requests recheck the completed settings after sampling, so a completed opt-out during that wait denies the response. As with pairing/session checks, this is a point-in-time check before writing the response, not an authority lease through delivery.

Responses use JSON and `Cache-Control: no-store`. Success has `version: 1`, `sampled_at_unix_ms` (wall-clock time at sample completion), `interval_ms`, `cpu: {cpu_usage_percent?}` and `gpus: [{id, name, metrics}]`. GPU metric keys are `gpu_usage_percent`, `gpu_encoder_percent`, `gpu_temperature_c`, `gpu_vram_used_mb` (MiB), and `gpu_vram_usage_percent`. Unknown/invalid readings are omitted; present zero readings are valid. Missing CPU usage on the first sample is expected until a counter delta exists. The timestamp and readings stay unchanged for all clients inside the interval. Sampling runs only when requested, with a two-second sample wait; no stream or overlay subscription is created.

GPU IDs are opaque signed 32-bit identities local to this host process/provider, not display indices, ADLX IDs, or an assertion about which GPU captures or encodes the stream. Do not persist IDs across reconnects/restarts or assume array order. This minimum exposes one explicitly identified device: Windows uses the selected DXGI adapter's matched PDH utilization and D3DKMT temperature/VRAM (adapter-matched PDH VRAM where available); unmatched NVML fallbacks are omitted. A replacement DXGI LUID receives a new ID; adapters without a dedicated-memory DXGI selection may be absent. Linux uses the existing NVIDIA NVML device handle (device 0); AMD/Intel Linux GPU readings and macOS GPU readings are currently unavailable. CPU usage uses each platform's existing provider on Windows, Linux and macOS. Unsupported or failed GPU reads yield an empty/partial GPU array, never synthetic zeros. Full multi-GPU enumeration is not implemented.

Errors carry an `error` string: 403 when disabled or the current paired viewer authority is absent; 409 without the same client's running video; 503 when busy, sampling fails, a provider is unavailable, or the two-second wait expires. Clients should stop polling after 403/409, back off after 503, clear unavailable values, and rediscover on reconnect. Keep at most one request in flight and poll no faster than `interval_ms`.

`interval_ms` is the current completed minimum request/cache interval, not a counter measurement window. A counter delta after an idle gap can span the gap. The two-second bound applies to waiting for the sample; a native provider call is not cancellable, and shutdown joins its single owned worker and can therefore wait indefinitely for a blocked provider. Windows preserves zero residency when a successful D3DKMT dedicated-segment reading supplies positive capacity; unavailable zero/zero results and unmatched NVML data remain absent from client GPU readings.

Vibepollo requires a current enabled paired certificate with View streams or Launch applications permission for discovery and requests. Session ownership uses that current certificate snapshot's exact UUID; request parameters and session history aliases cannot grant access. Real driver readings, TLS/session integration and client rendering require native/client acceptance testing; a host implementation alone does not supply a renderer.
