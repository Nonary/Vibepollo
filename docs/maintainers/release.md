# Release Vibepollo

Vibepollo stable and nightly releases share one numeric version sequence. Dispatch **Allocate stable
release** from `master` to reserve a version and build its exact annotated tag. Stable releases use
`stable` channel metadata; nightly releases use the same numeric tag shape with GitHub's prerelease
flag and explicit `nightly` metadata. New tags never use channel suffixes.

Linux release candidates are built from `master`. Every branch push builds and validates the
installable Arch/CachyOS package without creating a GitHub Release, updating the signed pacman
repository, or deploying the production Pages site. Download the `build-Archlinux` artifact from
the successful CI run for installation and MOK testing, and tag only a verified `master` commit.

## Version allocation

The allocator starts from the highest published Vibepollo version and counts each conventional
`feat` or `fix` commit once if it is not already reachable from any published release source. Each
feature advances minor and resets patch to zero; fixes advance patch when the delta has no feature.
Ten fixes after `2.0.6` produce `2.0.16`; one feature plus ten fixes produces `2.1.0`; two features
plus ten fixes produces `2.2.0`. A source with no eligible feature or fix is skipped, and an
unchanged source does not receive another release.

The allocator checks every published product version and matching tag, including old suffixed tags
and `v` aliases. It verifies ancestry from the latest published release source, highest-version
source, latest stable source and latest qualified prerelease source. Diverged history blocks
allocation until it is reconciled. Windows packaging permits major/minor values through 255 and
patch through 654; overflow fails without normalizing the count.

Each reservation is an annotated immutable tag whose message identifies `stable` or `nightly` and
the exact full source SHA. A retry reuses it only when version, channel and source all match. A
shared workflow concurrency group serializes allocation, builds and publication.

## Stable release

Dispatch **Allocate stable release** from current `master`. It reserves the annotated stable tag and
dispatches CI against that exact tag. CI revalidates the allocation, channel, ancestry and source
before building. Stable release notes are generated from the validated commit delta since the
previous published source.

After the tag build succeeds:

1. Open the **Sign and publish release** workflow.
2. Enter the exact numeric `release_tag` emitted by the allocator.
3. Leave the recovery run IDs empty during a normal release.
4. Enable `release_draft` for the first production releases so every asset can be inspected before
   publication.
5. Run the workflow and approve the external Windows signing request when required.

The workflow verifies retained artifacts and the annotated tag against the exact source and channel,
then rechecks the live release baseline immediately before publication. It publishes the GitHub
Release against the existing tag and includes the Arch package generated by that CI run.

## Verify the published release

- Confirm the GitHub Release is attached to the numeric source tag.
- Confirm its stable/pre-release classification matches the annotated tag channel.
- Confirm the release notes and every asset version match the tag.
- Download the Arch package on a clean Arch or CachyOS test machine and verify installation,
  executable capabilities, DKMS status, module signature, and managed-display startup.
- Verify the Windows signatures and installer provenance before publishing a draft.

## Publish the Arch Linux repository

For a non-draft release, run **Publish signed Arch repository** with the exact v-less
`release_tag`. The workflow downloads the release's single validated `vibepollo` package, checks
its embedded package name, version, and architecture, signs it, updates the signed `vibepollo`
database on the `arch-repo` branch, and pushes that branch. The Pages workflow then deploys it at
`https://nonary.github.io/Vibepollo/arch/x86_64`.

The `arch-repository` GitHub environment must contain:

- Environment secret `ARCH_REPO_GPG_PRIVATE_KEY`: the ASCII-armored private repository-signing key.
- Environment secret `ARCH_REPO_GPG_PASSPHRASE`: the private key's strong passphrase.
- Environment variable `ARCH_REPO_GPG_FINGERPRINT`: the full uppercase fingerprint with no spaces.

Protect the `arch-repository` environment with required-reviewer approval. Keep an offline backup
of the private key and its revocation certificate. Do not use a personal day-to-day signing key or
the Secure Boot/MOK module-signing key for this repository.

After publication, verify that the Pages deployment succeeds, import the published public key on a
clean Arch or CachyOS machine, add the `[vibepollo]` repository shown on the project site, and run
`pacman -Syu vibepollo`. A normal system upgrade must subsequently discover Vibepollo updates.
